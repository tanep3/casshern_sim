## 📝 要件定義 Draft v0.4（共通構造＋勝利条件＋操作）

### 1. ユニット共通ベース情報（フィールド案）

v0 時点で **全ユニットが必ず持つ**べき情報を整理すると：

* **ID**：ユニーク識別子
* **陣営（Side / Faction）**：アンドロ / 人類 / その他
* **キャラクタ種別（Archetype）**：

  * ブロッケンJr / 四天王 / 雑魚アンドロ（遠・中・近）
  * キャシャーン
  * 人類：将 / 佐 / 尉 / 兵 など
* **位置（x, y）**：2D 座標
* **向き（direction）**：向いている方向
* **HP / Max HP**：体力
* **移動速度（base_move_speed）**
* **現在の武器**（装備中の武器 ID or 種類）
* **現在の乗り物**（乗っている車・バイク・戦車など / 無し）
* **現在の防具**（甲冑など / 無し）
* **生存フラグ**（alive / dead）
* **制御モード**：

  * AI制御
  * プレイヤー制御（キャシャーンのみ）

> 🔹 乗り物・防具は「別エンティティ」として定義しつつ、
> ユニット側には「今なにに乗ってるか／何を着てるか」だけ持たせる構造が良さそう。

### 2. 種別 vs Trait の設計方針

ここがさっきの質問の肝だと思うから、ハッキリ線引きしておくね。

#### ◎ キャラクタ種別（Archetype）は「データ・ラベル」

* 例：

  * ANDRO_BOSS_BROCKEN
  * ANDRO_ELITE_FOUR
  * ANDRO_GRUNT_RANGED
  * HUMAN_GENERAL
  * HUMAN_SOLDIER
  * CASSHERN

これは

* 表示
* 初期ステータス決定
* シナリオ・UI
  で使う「**属性ラベル**」。

> 👉 **これは Trait ではなく enum（あるいはID）で持つのが素直。**

#### ◎ 階級（Rank）は「人類専用の属性」

* NONE / 将 / 佐 / 尉 / 兵 … など
* Rank 自体はラベルで、
  **「指揮権を持つかどうか」「どの範囲か」は Trait＋パラメータで決める**のが綺麗。

例イメージ（概念）：

* Rank = 将
* HasCommandAuthority（command_range = LARGE, command_power = 0.9）

→ 「将だから指揮権を持つ」のではなく、
　「Rank=将 かつ HasCommandAuthority を実装している」で指揮官扱い。

#### ◎ Trait は「行動・能力そのもの」

* 移動できるか / 攻撃できるか / 指揮できるか / 罠を扱えるか / 進化するか…
* 実際に処理として呼び出されるインターフェース。

> 💡 まとめると：
>
> * **種別・階級 = そのユニットが“誰か”というラベル**
> * **Trait = そのユニットが“何ができるか”という機能**

この切り分けなら、将来の拡張にも耐えやすい。

### 3. 勝利条件とゲームの終了制御

#### ◎ 勝利条件（Q6）

* **どちらかの陣営が全滅した時点で決着**

  * アンドロ側全滅 → 人類勝利
  * 人類側全滅 → アンドロ勝利

※ 将来的に「引き分け条件」や「時間制限」も拡張可能だが、
　v0 はシンプル全滅ルールで OK。

#### ◎ ストップ系 UI（最低限）

* **一時停止ボタン（Pause）**
* **再開ボタン（Resume）**
* **終了ボタン（Stop / End）**

  * 現在の戦闘を即時終了（結果を無視してもよい）
* **リスタートボタン（Restart）**

  * 同じパラメータで再スタート

→ 要件としては
「**決着がつかなくても、ユーザーがいつでも制御できること**」
を満たせば良い。

### 4. プレイヤーのリアルタイム操作範囲

* **リアルタイムで操作できるのはキャシャーンのみ。**
* 他ユニットは AI ベースで自律的に行動。

プレイヤーがキャシャーンにできる指示（要件）：

* 現時点のアイデア：

  * 行動モード切替：

    * 「敵の多い場所に突撃」
    * 「人類が集中攻撃されている地点を優先援護」
    * 「最寄りの敵をひたすら倒す」
  * 将来的に：

    * 移動目標地点の指定（クリックで移動先指示）
    * 「ボス優先」「雑魚掃討」などの優先ターゲット指定

> v0 の時点では
> **「モード切り替えだけでもゲームとして成立する」**
> ので、ここを最初のリアルタイム操作の中核にしてよさそう。

## ✅ ここまでのまとめ（タルモン見解）

* 複雑そうに見えるけど、
  **ラベル（種別/階級）と Trait（能力）の分離** ができているので、
  設計としてはかなり筋が良い。
* v0 ではフルスペック実装ではなく、
  「Traitの枠組み＋最低限の挙動」だけ固めつつ、
  段階的に中身を入れていく戦略が現実的。
* Rust＋WASM＋WebGPU 前提でも、
  この構造なら十分“持てる範囲”に収まる。
